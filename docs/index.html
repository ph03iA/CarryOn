Usage limits, handled locally

Keep your work going when the limit runs out

CarryOn is a small local program that watches your Claude Code and Codex plan usage every minute without sending a prompt. When a limit runs out it records the incident, waits for the reset, asks Gemini whether the cut-off session is worth continuing, and resumes that session by its ID. You get one email when the limit comes back, not when it runs out.

Windows, macOS, or Linux. Go 1.26 or newer. The watcher and the agents run on your own machine.

Part one

What CarryOn does

CarryOn reads plan usage from the tools you already use, with no prompt and no cost. A window that reaches 100 percent becomes one recorded incident, and the session that the limit cut off is identified from the local session logs. When the reset time the tool reported has passed, CarryOn asks Gemini for a single decision, and, if the decision is to continue, runs the provider's own resume command against that session ID in the session's own folder. Incidents, resumes, decisions, and the email outbox are written to a local SQLite database, every decision is logged with its reason, and one email tells you when the limit is back and what CarryOn did about it.

Part two

How it works

  1. The limit hits 100 percent. CarryOn records one incident for that provider, window, and reset time, and notes the session log that the limit cut off. No email is sent when a limit runs out.

  2. The reset time comes from the tool. When the limit hit 100 percent, the tool reported when it resets. Once that time passes, CarryOn acts without asking again, because a usage check can fail or come back empty. It only waits while the last good reading shows another limit, such as the weekly one, still at 100 percent.

  3. Gemini decides. The tail of the cut-off session, the folder, the limit, and the reset time go to Gemini, which returns one decision: resume, skip because the task looks done, or skip because the agent looked stuck.

  4. The back email goes out. One short email per limit with the subject Claude Code is back: resumed <folder> or Claude Code is back: no resume needed. It lists short bold labels: Project, Next step, Why, and a Continue by hand command when it resumed.

  5. The session resumes by ID. The agent runs in the session's folder against that session's ID, so it continues the same conversation rather than the newest one in the folder.

  6. There is no finish email. The post-run Gemini decision is stored and shown by carryon decisions. The back email goes out as minimal HTML with a plain-text fallback.

Part three

How the agent decides

Resume
Unfinished work remains. Gemini returns a concrete next step, which becomes the prompt for the resumed run.
The session stopped mid-refactor with a failing checkout test and a clear next step. The reply is resume with: Run the failing checkout test and finish the handler.
Skip because the task looks done
The work appears complete, so no usage is spent on a resume.
The last assistant message says the change is complete and the tests pass. The reply is skip_done, and the back email says: No resume was needed. Why: the task was already done.
Skip because the agent looked stuck
The agent was looping or blocked, so a person should look instead.
The log shows the same file edited five times with the same error. The reply is skip_stuck, and the back email says: No resume was needed. Why: the agent looked stuck.

Part five

Safety

  • A reset counts once the time the tool reported has passed and no other limit is still at 100 percent in the last good reading.
  • Resumes use the session ID, and CarryOn skips a session that was already continued after the cut-off.
  • Each limit hit allows at most two resumes for its cut-off session.
  • Claude, Codex, and the usage probes run in a kill-on-close sandbox: a Windows Job Object, or a process group that receives SIGKILL on macOS and Linux.
  • On macOS and Linux the group is killed as soon as the agent exits, so a dev server or watcher it started does not keep running. If CarryOn crashes mid-run, it kills the agent it left behind on its next start, as long as the machine has not rebooted since.
  • Both API keys are removed from every Claude and Codex process CarryOn starts.
  • Secrets are redacted from session text before it goes to Gemini, and email bodies are redacted again before Resend.

Part six

Setup

Run these commands from the cloned CarryOn folder, using the block for your operating system. Build CarryOn before running init or watch.

  • Windows 10 or 11, macOS, or Linux
  • Go 1.26 or newer
  • Claude Code signed in with a Pro or Max plan, and/or Codex signed in with a ChatGPT plan
  • A Gemini API key
  • Optional: a Resend API key. Without one, emails stay queued and carryon status --json shows them.

Choose a guide: real use with the watcher or simulation for testing.

Real use: watch for limits

  1. Clone the repository (skip this if you are already inside the cloned folder):

    macOS / Linux:

    git clone https://github.com/ph03iA/CarryOn.git && cd CarryOn

    Windows PowerShell:

    git clone https://github.com/ph03iA/CarryOn.git; cd CarryOn

  2. Build it:

    macOS / Linux:

    go build -trimpath -o carryon ./cmd/carryon

    Windows PowerShell:

    go build -trimpath -o carryon.exe ./cmd/carryon

    On Windows, this creates carryon.exe in the current folder. If PowerShell cannot find .\carryon.exe, complete this build step in the cloned folder first.

    If go env GOARCH prints 386, set GOARCH=amd64 first (PowerShell: $env:GOARCH = "amd64").

  3. Set your recipient, replacing you@example.com with your email:

    macOS / Linux:

    ./carryon init --email you@example.com

    Windows PowerShell:

    .\carryon.exe init --email you@example.com

    Run init --email again to change the recipient. Without --email, CarryOn keeps the saved address. The recipient is saved in config.json; .env holds your API keys.

    CarryOn watches both Claude Code and Codex by default. Add --providers claude or --providers codex to the init command to watch only one.

    To change providers later, stop the running watcher with Ctrl+C, rerun init with --providers claude, --providers codex, or --providers both, then start watch again. The watcher loads its settings at startup. If you use the background service, change providers with init first, then restart the service using the commands under Use it every day.

    Manually create a plain-text file named .env in CarryOn's state folder using any text editor:

    Windows: %APPDATA%\CarryOn\.env
    macOS: ~/Library/Application Support/CarryOn/.env
    Linux: ~/.config/CarryOn/.env (or $XDG_CONFIG_HOME/CarryOn/.env if set)

    Add these lines, replace your_gemini_api_key with your key from Google AI Studio, and save the file:

    GEMINI_API_KEY=your_gemini_api_key
RESEND_API_KEY=

    RESEND_API_KEY is optional. Fill it in to enable email delivery, or leave it blank to keep emails queued. ./carryon status --json shows the queued email.

    With the default sender onboarding@resend.dev, use the recipient email registered to your Resend account.

  4. Start the watcher from the CarryOn folder:

    macOS / Linux:

    ./carryon watch

    Windows PowerShell:

    .\carryon.exe watch

    Leave this terminal open and keep your computer awake. Use Claude Code or Codex normally in a separate window. If you are already limited, start the watcher before the reset: it must observe the exhausted quota to record the incident. You do not need to enter the reset time.

  5. Open another terminal in the CarryOn folder, check the state, and follow the logs:

    macOS / Linux:

    ./carryon status
./carryon log

    Windows PowerShell:

    .\carryon.exe status
.\carryon.exe log

    When a limit is hit, look for limit exhausted and cut-off session for claude or cut-off session for codex. If the log says no cut-off session was found, CarryOn retries at reset; it cannot resume without finding that session. Avoid manually continuing the same interrupted session while CarryOn is waiting.

  6. After the reset, check the decisions in another terminal:

    macOS / Linux:

    ./carryon decisions

    Windows PowerShell:

    .\carryon.exe decisions

    CarryOn polls every minute. Within a minute after the reset time, Gemini decides whether to resume the unfinished task or skip it.

Simulation: test a resume

Complete the build, init, and manual .env steps above first. Simulation uses your normal CarryOn configuration and fakes only the usage limit and its reset. You do not need to wait for a real limit, but Claude Code or Codex needs available usage to perform a resume.

This test makes real Gemini requests, can resume an agent and edit the selected project's files, and sends real email when configured.

  1. In a disposable project folder, start your signed-in Claude Code or Codex CLI. Ask for a small task with several steps, interrupt it while work remains, and exit the CLI.

  2. Wait at least two minutes after exiting. From the CarryOn folder, choose the command for the tool you used. CarryOn selects its newest session that has been inactive for at least two minutes.

    Claude Code, macOS / Linux:

    ./carryon simulate

    Claude Code, Windows PowerShell:

    .\carryon.exe simulate

    Codex, macOS / Linux:

    ./carryon simulate codex

    Codex, Windows PowerShell:

    .\carryon.exe simulate codex

  3. Check the provider, session ID, and folder shown in the confirmation prompt. Enter y only if they match your test session; enter n to cancel. The command labels the run SIMULATED.

  4. After the command finishes, check the result:

    macOS / Linux:

    ./carryon status
./carryon decisions

    Windows PowerShell:

    .\carryon.exe status
.\carryon.exe decisions

    Gemini may resume the unfinished task or skip work that looks complete or stuck. The recorded decision explains the outcome.

Use it every day

  • Optional: run go install -trimpath ./cmd/carryon, then add $(go env GOPATH)/bin (on Windows %USERPROFILE%\go\bin) to your PATH and restart the terminal so carryon works anywhere.
  • Install the background service with carryon service install. On Windows, run it from PowerShell opened with "Run as administrator" for the hidden S4U task; without admin you get a task that shows a console window. On macOS it writes ~/Library/LaunchAgents/dev.carryon.plist and loads it with launchctl. On Linux it writes ~/.config/systemd/user/carryon.service and enables it with systemctl --user.
  • On macOS and Linux, run carryon service install from a terminal where claude and codex work. The service records that terminal's PATH, because launchd and systemd start programs with a short PATH that misses ~/.local/bin, Homebrew and npm folders. Run it again if you move them.
  • Start and stop it:
# macOS
launchctl kickstart -k gui/$(id -u)/dev.carryon
launchctl kill SIGTERM gui/$(id -u)/dev.carryon

# Linux
systemctl --user restart carryon.service
systemctl --user stop carryon.service

On Windows:

Start-ScheduledTask -TaskName CarryOn
Stop-ScheduledTask -TaskName CarryOn
  • Check it with carryon service status and carryon log.
  • carryon reset needs the background service stopped first.

Live usage check, no prompt sent:

Part seven

Known limits

CarryOn runs on Windows, macOS, and Linux. The Claude Code usage request it relies on is experimental, so a Claude Code update can change it. Print-mode permissions can still block edits. Process containment differs by platform: Windows uses a Job Object, while macOS and Linux use process groups, so a child that leaves its group can survive, and Linux's Pdeathsig is a backstop rather than a guarantee. The macOS agent uses the legacy launchctl load interface, and the Linux unit needs a running user systemd manager. A machine that stays offline for a long time can lose or duplicate a queued email. A real Claude limit has been caught and its back email delivered, and Claude's real limit message matches the detector, but resuming a real cut-off session by itself has not been observed yet. The full list is in the Known limits section of the README.

Part eight

Privacy

Sent to Google

Gemini receives the tail of the cut-off session, about the last 4,000 tokens, plus the folder, the session ID, the limit and reset time, and the attempt count. After a run it receives the exit status, the diff stat, a bounded diff excerpt, test output when tests ran, and the last message.

Credential-shaped text is redacted before sending, and the session text is wrapped in delimiters that tell the model to treat it as data.

Sent to Resend

Resend receives the recipient, the sender, the subject, and the body, in minimal HTML with a plain-text fallback. When CarryOn resumed, the body holds the folder name, the next step, the reason, and the "Continue by hand" command. When it did not resume, the body holds the folder name, if any, and a plain-word reason.

It contains no reset times, full paths, changed file names, agent messages, exit codes, or test output. Email bodies are redacted again before they are sent.

Stays on this machine

Usage readings, incidents, resume records, decisions, the email outbox, the session logs, the configuration, and both API keys stay in the local state folder: %APPDATA%\CarryOn on Windows, ~/Library/Application Support/CarryOn on macOS, and ~/.config/CarryOn on Linux. CarryOn makes no other network calls.

It never opens ~/.claude/.credentials.json, ~/.codex/auth.json, or a keychain entry, and it never prints a token.
